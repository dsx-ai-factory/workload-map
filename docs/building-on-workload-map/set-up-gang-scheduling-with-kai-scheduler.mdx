Gang scheduling admits all the pods of a distributed workload together, or none of them.

[KAI Scheduler](https://github.com/kai-scheduler/KAI-Scheduler) is an open source Kubernetes scheduler for AI and GPU workloads. Its pod grouper creates a pod group for each workload. For a workload type that has no native KAI plugin, the pod grouper reads the gang scheduling instructions in a Workload Map definition. A definition therefore gives any custom resource correct pod grouping in KAI Scheduler, with no scheduler plugin to write.

This guide shows how to add gang scheduling instructions to a definition, apply it, and check the result in KAI Scheduler.

<Warning title="Experimental">
This part of the API is experimental and may change.
</Warning>

## How KAI Scheduler Uses a Definition

KAI Scheduler selects the pod grouper for a workload in the following order:

1. If a native KAI plugin matches the group, version, and kind of the workload, KAI uses the native plugin.
2. Otherwise, KAI looks for a matching Workload Map definition.
3. If the definition is valid and contains gang scheduling instructions, KAI uses the Workload Map plugin.
4. Otherwise, KAI uses the default pod grouper.

The plugin translates the definition into a regular KAI `PodGroup`. KAI scheduling continues to operate on the generated `PodGroup`, so it needs no Workload Map specific scheduling primitives. KAI evaluates no jq path itself. The Workload Map library evaluates the paths of the definition.

The `podGroup` instruction maps to the `PodGroup` of KAI as follows:

| Definition field | KAI PodGroup field | Notes |
| --- | --- | --- |
| `podGroup.name` | The pod group name | The exact name follows the naming rules of the KAI pod grouper. |
| `podGroup.topology` | The topology constraint of the pod group | Applies to all pods in the pod group. |
| `podGroup.subGroups[].componentName` | A subgroup, and its pod membership | KAI creates one subgroup for each listed component. The subgroup name is the component name. |
| `scaleDefinition.minReplicasPath` or `scaleDefinition.replicasPath` of the component | The `minMember` of the subgroup | KAI uses the minimum replica count when the definition provides it, and the replica count otherwise. |
| The number of items in `podGroup.subGroups` | The `minSubGroup` of the pod group | KAI sets it only when it creates subgroups. |
| `podGroup.subGroups[].topology` | The topology constraint of the subgroup | Applies only to the pods of that component. |

KAI also keeps the standard metadata that its pod grouper handles, such as the namespace, owner references, queue, priority, labels, annotations, and preemptibility.

## Prerequisites

- KAI Scheduler v0.19.0 or later. The Workload Map plugin shipped in KAI Scheduler v0.17.0. Release v0.19.0 changed KAI to find definitions under the label keys that the Karta Operator stamps.
- The generic fallback enabled in the KAI pod grouper. The `generic-karta-fallback` option is `true` by default.
- The `Karta` CRD and the Karta Operator installed in the same cluster. For more information, refer to [Installation](../getting-started/installation.mdx#install-the-karta-operator).
- A workload type that has no native KAI plugin. A native plugin takes precedence over a definition.

KAI finds a definition by the group, version, and kind of its root component. It matches them against three labels on the `Karta` object: `karta.run.ai/group`, `karta.run.ai/version`, and `karta.run.ai/kind`. The Karta Operator stamps these labels on each definition. Its admission webhook stamps them when you apply a definition, and its reconciler adds them to definitions that were created while the webhook was disabled.

## Add Gang Scheduling Instructions

Add `optimizationInstructions.gangScheduling.podGroup` to the definition of your workload type. The group gets a name, and each listed component becomes a subgroup. The following example is the PyTorchJob definition with a pod group that has two subgroups, one for the master and one for the workers:

```yaml
optimizationInstructions:
  gangScheduling:
    podGroup:
      name: job
      subGroups:
        - componentName: master
        - componentName: worker
```

Each entry in `subGroups` must meet the following conditions:

- `componentName` matches a component that the definition declares.
- The component defines its replica count with `scaleDefinition.replicasPath`, and optionally `scaleDefinition.minReplicasPath`. KAI uses it as the minimum number of pods of the subgroup.

To ask KAI to place the pods close together in the cluster topology, add a `topology` constraint. Set it under `podGroup` for all pods, or under a subgroup for the pods of that component:

```yaml
optimizationInstructions:
  gangScheduling:
    podGroup:
      name: job
      subGroups:
        - componentName: master
        - componentName: worker
      topology:
        topologyName: rack-topology
        preferredTopologyLevel: rack
        requiredTopologyLevel: zone
```

The topology name and the levels in this example are placeholders. Use the names of a topology resource that exists in your KAI Scheduler installation.

A topology constraint has three required fields:

| Field | Meaning |
| --- | --- |
| `topologyName` | The topology resource that the constraint uses. |
| `preferredTopologyLevel` | The preferred locality level. |
| `requiredTopologyLevel` | The maximal level that all matching pods must fit within. |

<Warning title="kli validate does not check podGroup">
The `kli validate` command checks that the members of the older `podGroups` format name existing components. It does not run that check on `podGroup`. Check by hand that every `componentName` under `subGroups` matches a component of the definition.
</Warning>

## Understand the Limits of the Integration

The KAI integration keeps the generated structure simple:

- KAI creates no elastic pod groups and no elastic subgroups.
- KAI creates no nested subgroups, and no `minSubGroup` inside a subgroup.
- KAI creates one subgroup for each component. All the pods that match a component attach to the subgroup of that component, whatever their grouping key.

A component that uses a `componentInstanceSelector` or a `replicaSelector` is a poor candidate for a subgroup. It can still take part in the pod group, but one subgroup can hide the structure of its instances. For these selectors, refer to [Define a Workload Type](../building-on-workload-map/define-a-workload-type.mdx).

### The Older podGroups Format

KAI still supports the older `gangScheduling.podGroups` list format, and the catalog definitions that were written before `podGroup` still use it. If a definition has both formats, KAI uses `podGroup`. The older format has the following behavior:

- Multiple pod groups of the older format do not schedule together as one unit.
- Write the filters so that each pod belongs to only one generated pod group.
- Subgroups and topology constraints exist only in the `podGroup` format.

The two formats are not equivalent. A member of `podGroups` has `groupByKeyPaths` and `filters`. A subgroup has only `componentName` and `topology`, so a grouping key or a filter has no direct counterpart. Write new definitions in the `podGroup` format.

## Apply the Definition and Check the Result

1. Validate the definition:

   ```bash
   kli validate my-workload.yaml
   ```

2. Apply the definition to the cluster:

   ```bash
   kubectl apply -f my-workload.yaml
   ```

3. Check that the Karta Operator stamped the labels that KAI uses to find the definition:

   ```bash
   kubectl get karta <name> --show-labels
   ```

   The output includes `karta.run.ai/group`, `karta.run.ai/version`, and `karta.run.ai/kind`.

4. Submit a workload of your type, with the scheduler name that your KAI Scheduler installation uses.

5. Check the pod group that KAI created:

   ```bash
   kubectl get podgroup -n <namespace> -o yaml
   ```

   The `PodGroup` has the `minMember` and `minSubGroup` fields, and a `subGroups` list that matches your definition. A topology constraint appears in the `topologyConstraint` field.

KAI skips a definition in the following cases, and then it uses the default pod grouper:

- The definition has no gang scheduling instructions.
- The definition is not valid.
- The definition is being deleted.
- More than one definition with gang scheduling instructions matches the same group, version, and kind. KAI logs an error for the workload type.
