The DSX Workload Exporter reports the status of workloads and maps each pod to its workload, component, instance, and group. Prometheus can join these labels with CPU, memory, and GPU measurements from other exporters. This guide sets the options that most installations change and connects Prometheus to the exporter.

## Prerequisites

- The exporter installed in the cluster. For more information, refer to [Installation](../getting-started/installation.mdx#install-the-dsx-workload-exporter).
- Prometheus. To use the `ServiceMonitor` in this guide, Prometheus Operator and its `ServiceMonitor` CRD must be installed.
- DCGM and cAdvisor measurements in Prometheus, only if you want to join the exporter labels with GPU, CPU, and memory data.

## Apply a Configuration Change

The chart writes the exporter settings into a ConfigMap, and the exporter reads them when it starts. The chart restarts the pod when the settings change.

To change a setting, put it under the `exporter` key in a values file, such as `values.yaml`. Then run the `helm upgrade --install` command from [Installation](../getting-started/installation.mdx#install-the-dsx-workload-exporter) again, with `-f values.yaml` added.

## Choose Which Namespaces to Observe

By default, the exporter observes all namespaces except `kube-system`, `kube-public`, and `kube-node-lease`. To observe only the namespaces that carry a label, set `namespaceSelector`. The following example observes only the `workloads` namespace:

```yaml
exporter:
  namespaceSelector:
    matchLabels:
      kubernetes.io/metadata.name: workloads
    matchExpressions: []
```

Setting `matchExpressions: []` removes the default exclusion of the three system namespaces.

Namespace selection limits the namespaced objects that the exporter observes. It does not limit cluster-scoped resources or the permissions that the chart grants.

## Connect Prometheus

The exporter serves its metrics at `/metrics` on port 8080. Prometheus pulls them. The exporter does not push metrics with OTLP. To send the metrics to an OTLP backend, use an OpenTelemetry Collector that you configure to scrape `/metrics` and forward the data.

To let an existing Prometheus Operator discover the exporter, enable the `ServiceMonitor` of the chart:

```yaml
exporter:
  serviceMonitor:
    enabled: true
    additionalLabels:
      release: prometheus
```

Follow these rules:

- Set `additionalLabels` to the label that your Prometheus uses to select `ServiceMonitor` objects. The value `release: prometheus` is an example.
- Prometheus must select the namespace and the labels of the `ServiceMonitor` through `serviceMonitorNamespaceSelector` and `serviceMonitorSelector`.
- The chart does not install Prometheus Operator, Prometheus, or their CRDs. A `ServiceMonitor` does not configure a standalone Prometheus server.
- Keep `honorLabels: true`. The `namespace` label of the exporter is the namespace of the workload. Without `honorLabels`, Prometheus moves the value to `exported_namespace`. The chart sets it for you. If you write your own `ServiceMonitor`, set `honorLabels: true`. In a Prometheus `scrape_config`, set `honor_labels: true`.
- The `Prometheus` resource must not set `overrideHonorLabels: true`, because it makes the Prometheus Operator ignore `honorLabels` on every `ServiceMonitor`.

The `/metrics` endpoint has no built-in authentication, and the chart does not create a network policy. Configure network access for your monitoring system.

## Size the Exporter for a Large Cluster

By default, the exporter requests `500m` CPU and `512Mi` memory, and its limits are `2` CPU and `4Gi` memory. The number of watched objects, the size of the objects, and the scrape frequency affect the usage. On a large cluster, measure the CPU and memory usage of the exporter, and raise `exporter.resources` to match.

If the container is killed for memory, raise `exporter.resources.limits.memory`. The default value `auto` of `exporter.goMemLimit` follows that limit.

## Check That the Data Is Valid

A successful scrape does not show that the observations are valid. To check the data, use the following labels and metrics:

- Filter `dsx_workload_pod_info` and `dsx_workload_status` by `observation_valid="true"`. The value `false` marks a retained observation whose evaluation or dependencies failed.
- Read `dsx_exporter_observation_valid` for the health of the collection and for the reasons that a workload failed.

The following query lists the workloads that are running and whose observation is valid:

```promql
dsx_workload_status{phase="Running",observation_valid="true"} == 1
```

A workload can have a valid status even when its phase is `Failed`.
